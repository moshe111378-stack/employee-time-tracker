# העלאת משמרון ל־TestFlight

המסלול נמצא בענף `mishmaron-ios-preparation` בלבד. גרסת האפליקציה היא `1.2.0`, המזהה `il.co.mishmaron.app`, ורשומת App Store Connect היא `6820580792`.

## מצב מאומת לפני הוספת המסלול

הרצה `37935577638`, בקומיט `abe93e765076e27681188eb69e8d0d17c25a4a67`, הצליחה עם Xcode 26.3: ארכיון ללא חתימה, שלוש בדיקות NavigationPolicyTests ובדיקת מסכים בסימולטור. בדיקת המסכים פותחת את הבית, עוברת לעובדים, חוזרת לבית ופותחת את טופס כניסת המנהלים. היא אינה מתחברת כמנהל ואינה מדווחת נוכחות.

מסלול החתימה החדש טעון אימות ראשון עם הרשאות Apple תקפות. עצם שמירתו במאגר אינה הוכחת חתימה, העלאה או זמינות ב־TestFlight.

## חיבור Apple

נדרש חשבון Apple Developer פעיל, הרשאות API מתאימות ליצירת פרופילים וחתימה אוטומטית, וגישה לרשומת משמרון. יש לבדוק הרשאות קיימות לפני יצירת מפתח חדש. אם המפתח הקיים אינו מורשה לחתימה, ההרצה תיעצר; אין לבטל תעודות קיימות שמשמשות גרסאות אחרות.

ב־GitHub, בהגדרות המאגר → Secrets and variables → Actions, יש להגדיר:

| Secret | תוכן |
| --- | --- |
| `MISHMARON_TEAM_ID` | Team ID של Apple Developer, עשרה תווים |
| `ASC_KEY_ID` | מזהה מפתח API של App Store Connect |
| `ASC_ISSUER_ID` | Issuer ID של Team API key |
| `ASC_PRIVATE_KEY_BASE64` | תוכן קובץ `.p8` מקודד ל־Base64 |

מפתח `.p8` הוא סוד. אין לשלוח אותו בצ׳אט, להכניסו לקוד או לשמור אותו כ־artifact. מעבירים אותו רק בהגדרת הסוד המאובטחת. ניתן לקודד במק עם `base64 -i AuthKey_KEYID.p8 | pbcopy` ולהדביק ישירות בשדה הסוד.

הסקריפט משתמש ב־Xcode automatic provisioning/cloud signing ובמחזיק מפתחות זמני. הוא אינו תלוי בשחזור מפתח החתימה הישן, אך הצלחת החתימה תלויה בהרשאות ובמצב חשבון Apple בפועל. קובץ ה־API ומחזיק המפתחות הזמני מוסרים בסיום.

## הפעלה

1. לבדוק ב־App Store Connect מספר Build פנוי עבור גרסה 1.2.0. ברירת המחדל בטופס היא 9; אין להניח שהוא פנוי בלי לבדוק.
2. ב־GitHub Actions לבחור `Mishmaron iOS verification` → `Run workflow`, לבחור ענף `mishmaron-ios-preparation`, לסמן `upload_testflight` ולמלא `build_number`.
3. אם כפתור ההפעלה אינו מופיע כי קובץ workflow אינו קיים בענף ברירת המחדל, אין למזג את ענף ההכנה ל־main כדי להציגו. ניתן להריץ את הסקריפט בסביבת Mac מורשית אחרי אותן בדיקות, או להכין בנפרד שינוי CI בלבד לענף ברירת המחדל לאחר בדיקת ההשפעה.
4. משימת `verify` חייבת לעבור לפני משימת `testflight`. דחיפה רגילה לענף מריצה אימות בלבד ואינה מעלה Build.
5. המשימה החתומה בונה Archive, מוודאת מזהה וגרסה, מייצאת IPA ובודקת חתימה לפני פקודת ההעלאה. כישלון בכל שלב עוצר את ההמשך.
6. לאחר הצלחת פקודת ההעלאה, לפתוח TestFlight ברשומה `6820580792` ולוודא שה־Build המתאים סיים עיבוד. אין להסיק זמינות לבודקים מהצלחה ב־GitHub בלבד.

הפעולה מעלה Build בלבד; אינה שולחת App Review ואינה מפרסמת בחנות.

## בדיקה לאחר שה־Build זמין

להתקין את ה־Build המסוים ב־TestFlight על iPhone ולבדוק בארגון בדיקה:

- מסך ראשי נטען.
- מעבר לכניסת עובדים ופתיחת דיווח נוכחות.
- חזרה למסך הראשי.
- פתיחת כניסת מנהלים והתחברות עם חשבון בדיקה מורשה.

יש לרשום מספר Build, דגם מכשיר, גרסת iOS ותוצאות. בדיקת סימולטור קודמת אינה תחליף לבדיקה זו. אין לבצע דיווח נוכחות או לשנות עובדים בארגון פעיל לצורך הבדיקה.

לפני פרסום ציבורי נותר להשלים את הפרטים והבדיקות שב־`APP_STORE_PREPARATION.md`, כולל פרטיות, תמונות מסך, מחיקת חשבון ובדיקות הרשאות על מכשיר.
